# 模組 05：HPC 叢集建置與管理自動化

[能力路線](ROADMAP.md)｜職缺核心：HPC 叢集建置與管理自動化；支撐能力：Linux、網路與獨立作業。

## 先教會的概念

自動化不只是把人工命令串起來。inventory 描述目標節點和角色，playbook 描述期望狀態，template 依變數產生設定，handler 只在有變更時重啟服務，role 把同一能力的設定收在一起。冪等表示重跑不產生不必要變更；能執行第二次並不代表已冪等。安裝、設定、驗證和復原要是同一流程的一部分。秘密與一般設定分離，不能把驗證金鑰或雲端憑證提交進庫。

例：第一次部署建立設定並啟動 slurmd；第二次若設定未變卻仍每次重啟 slurmd，就要查 playbook 是否誤判變更，而不是只看退出碼為零。

## 指令先講清楚，再操作

ansible-inventory 用來確認節點分組與變數，ansible-playbook 執行部署；--check 是預演部分可支援的變更，不等於真的能部署成功，--diff 可能顯示敏感設定，須審慎使用。實際部署後要再跑一次並看變更數量、失敗節點與工作功能。具體套件模組和版本在環境確認後選，不預設所有發行版相同。

## 實作主線與過關證據

先將模組 1、4 人工確認過的 CPU／GPU 節點角色、服務帳號、驗證、共享路徑及 Slurm 設定轉為 Ansible。GPU 節點需管理已驗證的驅動安裝方法與版本、Slurm GRES 資源描述和服務重啟順序；不同機型或驅動版本不可盲套。先教 GRES 是排程器如何表示 GPU 等通用資源，以及工作為何要明確請求 GPU。保留作業系統和套件版本、人工前置條件及預期的重啟。從乾淨實驗 VM 部署，提交 CPU 工作與明確請求一張 GPU 的工作，核對執行主機、CUDA_VISIBLE_DEVICES、裝置利用與計算結果；第二次部署調查每個非預期變更。再用可恢復的節點暫時不可達或服務重啟案例，驗證重跑與功能恢復。改動前確認無重要工作，且每次清楚說明會變更哪些主機。

project/ansible/ 有可讀的部署程式、非敏感 inventory 範例與版本要求；project/docs/ 有實際重建步驟。過關不是服務顯示 active 或 nvidia-smi 有卡，而是從乾淨環境重建、CPU 與 GPU 工作各能由 Slurm 正確排到目標節點、重跑沒有未解釋變更、失敗後可安全恢復。只用一張 GPU 可驗證單卡資源分配，不能聲稱多卡隔離或 GPU 間通訊已驗證。

開始帶練前，先在本文件追加本次確定的 VM 指令、目的、目標主機、檔案與服務影響；執行後記錄真實結果。
