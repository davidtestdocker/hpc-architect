# 模組 06：叢集維運、Zabbix 監控與故障復原

[能力路線](ROADMAP.md)｜對應叢集維運、故障定位與管理能力。

## 要解決的問題與交付物

已有的控制節點和 GPU 運算節點能透過 Slurm 執行工作。
本模組要處理的是：運算節點出問題時，如何及時發現、找出原因、恢復排程，
並用同一份有已知答案的工作確認叢集真正恢復。

交付一條完整的證據鏈：**持續監控 → 故障告警 → Slurm 與服務定位 →
修復 → 告警恢復 → 工作結果核對**。Zabbix 要實際收集叢集資料並產生
故障及恢復事件；單張儀表板截圖不算完成。

## 目前狀態與已有基礎

**未開始實作。** 模組 01 已做過單節點控制服務停止與復原；
模組 02 已有提交前健檢 CLI；模組 05 已用 Ansible 部署兩節點 Slurm，
並執行可核對答案的 L4 工作。本模組沿用這些成果，重點放在
**跨節點故障的持續監控、告警與工作恢復**，不重做單節點服務演練，
也不為增加案例數重複名稱解析、權限或資源請求練習。

## 需要看見哪些狀態

| 層次 | 要回答的問題 | 本模組要留下的證據 |
|---|---|---|
| 服務 | 控制端和運算端的 Slurm 服務是否運作？ | 服務狀態、必要日誌與時間 |
| 排程 | 運算節點是否能接受工作？ | 節點狀態及故障原因 |
| 監控 | Zabbix 是否持續收集資料並辨認故障？ | 故障前後的資料、Problem 與 OK 事件 |
| 工作 | 修復後能否再次完成 GPU 工作？ | 執行節點、退出狀態與已知答案核對 |

Zabbix 的 **item** 是持續收集的數值或狀態，**trigger** 判斷何時有問題，
**event** 記錄問題出現與恢復的時間。監控資料與 Slurm 自己的狀態
要互相對照；服務重新啟動後，仍須由實際工作驗證排程和 GPU 通路。

## 實作順序與過關證據

1. 核對當時的控制節點、GPU 節點、Slurm 狀態及現有工作。
   GPU 節點若已停止，先確認啟動費用和本次使用時間。
2. 確認 Zabbix 版本、部署位置與資源需求，再部署監控。
   至少持續收集一項與運算節點或 Slurm 服務直接相關的狀態，
   設定能對應該狀態的告警及恢復條件。
3. 選一個可復原的**運算節點故障**。在確認沒有重要工作後，
   記下影響與復原方式，再進行演練；不破壞驅動或硬體。
   具體故障與指令須依實際服務及監控設定決定。
4. 保留同一次故障的 Zabbix Problem 事件、Slurm 節點狀態、
   服務狀態與日誌，據此定位並修復。接著核對 Zabbix 的 OK 事件，
   重新提交模組 05 的已知答案工作，核對節點、退出狀態與結果。

過關須能按時間串起**監控資料、告警、故障原因、修復動作、恢復事件和工作結果**。
Zabbix 的非敏感設定保存在 `project/monitoring/`；真實演練紀錄放在
`project/incidents/`。若現有健檢 CLI 缺少這次定位必需的跨節點檢查，
才擴充 `project/healthcheck/`，並驗證正常、故障及查詢失敗時的結果。

GKE 工作與 Slurm 的比較安排在模組 07；本模組聚焦現有叢集的監控與復原。
開始實作前，先在本文件記下確定要執行的命令、目標節點、影響及復原方式；
實際執行後才記錄輸出與判讀。
