# 模組 06：叢集維運、監控與故障復原

[能力路線](ROADMAP.md)｜支撐核心工作：獨立維運叢集；加分項：Zabbix。

## 這個模組在做什麼

用主機、服務、排程、工作和 GPU 的實際證據定位故障，
修復後重新執行工作確認恢復。監控要能持續提供資料，
讓告警指出需要處理的問題與恢復狀態。

## 目前狀態

**未開始實作。** 本文件記錄維運檢查與故障復原的目標。

## 先分清楚「健康」指什麼

| 層次 | 要回答的問題 | 只看上一層會漏掉什麼 |
|---|---|---|
| 主機 | VM 能否連線？ | 主機可連不代表服務可用 |
| 服務 | `slurmctld`、`slurmd` 等是否運作？ | 服務運作不代表節點能接工作 |
| 排程 | 節點是否可用、工作是否獲得資源？ | 獲得資源不代表答案正確 |
| 工作 | 輸出與退出狀態是否符合預期？ | 須再核對輸入、版本和執行節點 |
| GPU | 驅動可見、Slurm 可分配、工作真用到卡？ | `nvidia-smi` 有卡只證明第一層 |

例如，VM 可 SSH 且 `slurmd` 是 `active`，若節點為 `DRAIN`，
仍不能接新工作；要看節點原因，恢復後再提交工作驗證。

## 指令用途

本模組尚未執行下列檢查；此表只說明各工具能提供哪一層證據。

| 指令或工具 | 查什麼 | 判讀限制 |
|---|---|---|
| `systemctl status`、`journalctl -u` | 服務狀態與日誌 | 服務 `active` 不保證工作可完成 |
| `sinfo`、`scontrol` | 節點及其原因 | 節點可用仍須驗證實際工作 |
| `squeue` | 工作等待或執行狀態 | 要結合工作輸出與退出碼 |
| `nvidia-smi` | 驅動、卡與當下使用情況 | 看見卡不等於 Slurm 已分配給工作 |
| 健檢 CLI | 整理多項檢查 | 逾時與未知不能寫成正常 |

若環境支援，再評估 DCGM：先區分被動收集的健康資料，
與會占用資源的主動診斷。Zabbix 的 host、item、trigger、event
分別是監控對象、資料、告警條件和事件；它是加分項，無須先於核心維運能力。
實際命令與版本在環境確認後才加入。

## 實作與過關證據

1. 擴充 `project/healthcheck/` 工具，查節點、Slurm 與 GPU；保留逾時、部分失敗和未知狀態。
2. 先用原生狀態與日誌定位，再演練可復原的名稱／連線、共享路徑／權限、服務或節點不可用。
3. 核對 GPU 工作請求與節點 GRES 不符時的排程現象；不以破壞驅動或硬體壓力測試製造故障。
4. 每次先確認沒有重要工作，記下影響及復原方法，再操作；修復後用 CPU／GPU 工作復測。
5. 若做 Zabbix，再驗證資料持續更新、告警觸發及恢復，而非只留單次畫面。

預期交付為 `project/incidents/` 的真實事件紀錄、
`project/healthcheck/` 的程式與測試，以及工作前、中、後的 GPU 觀測證據。
若實做 Zabbix，非敏感設定再放 `project/monitoring/`。
核心過關以定位、修復和工作復測為準；Zabbix 是可選的加分實作。

開始實作前，先在本文件寫下確定要執行的命令、目標節點、影響及復原方式；
執行後只記必要輸出與判讀。
