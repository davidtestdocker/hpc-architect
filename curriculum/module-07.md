# 模組 07：效能證據與軟硬體架構取捨

[能力路線](ROADMAP.md)｜職缺核心：HPC 軟硬體集群架構規劃；支撐能力：計算機系統架構。

## 先教會的概念

吞吐量是單位時間完成多少工作，延遲是單次工作需多久；網路、儲存與工作啟動都可能成為瓶頸。加速比是基準時間除以新配置時間，效率還要考慮使用的資源數；小工作可能因通訊、CPU→GPU 資料傳輸與啟動成本而變慢。CPU 核心／記憶體容量、GPU 顯示記憶體、NUMA、PCIe、NIC、共享儲存與工作型態之間有取捨。單卡 GPU VM 可量測單卡工作，但不能驗證多 GPU 的 NVLink、跨 GPU 通訊、RDMA、實體交換器或機櫃供電。

例：序列版 10 秒、兩個 rank 版 6 秒，加速比是 10/6 ≈ 1.67，不是「用了兩個 rank 就加速兩倍」；還要看輸入大小與量測波動。

架構方案要說明工作需求、CPU／GPU 節點比例、每卡記憶體、資料路徑與網路容量、節點角色、身分／安全、儲存、監控、單點故障、備份／復原、供電／散熱假設與擴充路徑。GPU 型號要依負載型態區分：單卡排程與推論驗證可用 L4 類型，FP64 科學計算或多卡訓練需另評估 A100／其他適合型號；不能把單卡結果外推到大規模 GPU 叢集。Slurm 管作業排程，K8s 管容器工作負載，OpenStack 提供 VM 基礎設施；這是角色比較，不是宣稱三者互斥或可直接互換。K8s／OpenStack 屬職缺加分範圍，核心作品前不部署完整平台。

## 指令先講清楚，再操作

time 或工作系統紀錄提供耗時；lscpu、/proc 與檔案系統統計輔助定位資源；必要時再選 perf、網路或 I/O 量測工具，先說明採樣開銷與權限。量測命令、輸入大小、rank 數、節點位置、版本與重複次數都要固定記錄；只有一個漂亮數字不能推論可擴充性。

## 實作主線與過關證據

用模組 3 的工作負載，對至少兩種 CPU 配置各重複量測三次；GPU 工作則比較 CPU 與單 GPU 執行的正確性、資料量、耗時與裝置使用，保留原始 CSV、版本和環境。不同實作若演算法或精度不一致，不拿耗時直接宣稱加速。分析瓶頸、加速或變慢的原因，提出下一個可驗證改進。再做一份「若從教學 VM 擴到企業叢集」的設計：按工作型態估算 CPU／GPU／記憶體／儲存／網路與電力需求，說明控制器、GPU 節點或共享儲存失效時的影響，提出高可用、成本與維運取捨，標出需實體硬體或廠商文件才能確認的假設。可用架構問答練習獨立作業與溝通，不要求畫無用途的圖。

project/benchmarks/ 留原始資料及再生分析方法，project/docs/ 留架構決策。過關時能解釋量測限制、容量如何估、不同技術各解決什麼問題，以及哪些結論只是推估而非已驗證。

開始帶練前，先在本文件追加本次確定的 VM 指令、目的和檔案影響；執行後記錄真實量測。
