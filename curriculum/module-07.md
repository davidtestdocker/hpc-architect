# 模組 07：面試作品與職缺能力證據

[能力路線](ROADMAP.md)｜目標：把核心工作與程式能力整理成可檢查的作品。

## 要解決的問題與交付物

面試官需要分清作品中哪些叢集由設定實際建成、哪些只是設計，
以及遇到變更或故障時能否獨立判斷。本模組把前面的程式、部署與
事件紀錄整理成可重建、可追問的作品；再用一次新環境重建和
技術問答驗證操作能力，對照職缺準備履歷與展示。

## 目前狀態

**未開始實作。** 本文件記錄作品重建與面試展示的目標。

## 作品要讓別人看見什麼

作品應讓別人依文件重建、測試，並能追問每個設計決定。
檔案、命令結果與原始資料要能支持履歷中的說法：

| 履歷主張 | 需要的證據 |
|---|---|
| 設計叢集 | 需求、拓撲、資源與成本取捨 |
| 部署叢集 | 新環境重建的前置條件、實際節點與工作結果 |
| 網路系統設定與管理（核心工作） | 私有網路、Cloud NAT、DevStack 客體的 SNAT／DNAT 與服務連線、開機後通路恢復的設定及實測結果 |
| 網路管理與分析（加分條件） | 以位址、路由、連線方向與埠的檢查結果定位 SSH、NFS、Slurm 跨節點通路；說明封包去回程與故障判讀 |
| 自動化 | Slurm／Ansible 的設定來源、重跑、可控變更與人工依賴 |
| 維運與復原 | 真實事件的症狀、定位、修復及工作復測 |
| 架構選型 | 可比的原始量測、容量估算、網路／儲存與故障範圍取捨 |
| Zabbix 維運 | 持續更新的監控資料、告警觸發及恢復紀錄 |
| OpenStack | 已供給 `compute-cpu01`，核對管理連線，並以 Slurm CPU 工作驗證納管結果 |

例：若只完成跨節點工作，就寫「建置並驗證跨節點工作」；
沒有改善前後量測，就不能寫「優化叢集效能」。
教學規模 GCP 叢集可證明方法與操作，不能代表企業硬體規模、
實體高速網路或多年工作經驗，也不能虛構合作經歷。

## 檢查方式

下表是未來交付作品時的檢查方式，並非已完成的驗證。

| 材料 | 讀者要能做什麼 |
|---|---|
| Git 提交或版本標籤 | 找到與展示對應的交付版本 |
| README／操作手冊 | 找到安裝、執行、測試與復原步驟 |
| 工作輸出與原始資料 | 核對節點、結果、退出碼與量測數字 |
| 能力對照表 | 看清每項職缺要求有哪些證據、哪些尚未驗證 |

檢查命令應對應實際程式和部署文件；
不以一條「總測試成功」取代排程、網路、GPU、重建與故障驗證。

## 實作與過關證據

1. 列出重建範圍與既有前置資源。在新環境依文件重建 Slurm 叢集，
   核對 CPU／GPU 節點、共享資料、程式答案、GPU 分配與部署重跑。
   若費用或配額限制使某部分未重建，明確降低該部分的履歷主張。
2. 不依賴聊天紀錄，按 README 與操作手冊找到重建、工作驗證和
   故障復原步驟；記下缺漏的前置條件並修正文件，再核對實際結果。
3. 對照可取得的職缺內容逐項寫「要求 → 實際證據 → 未驗證範圍」，
   把 OpenStack 單台 VM 供給與納管、教學規模 Slurm 叢集
   和企業實體叢集經驗分清楚；未實作的工具不列為履歷能力。
4. 準備約十分鐘展示，聚焦需求、架構、叢集自動化、網路通路的
   設定與故障判讀、跨節點與 GPU 工作，以及設計取捨；
   量測只用來支持相關決策。
5. 做一次技術追問演練：現場修改 Python 或 C/C++，定位 Slurm
   工作或 GPU GRES、網路／資料路徑故障；依位址、路由與連線結果
   說明通路的去回程，並說明選用 Slurm 的理由、
   OpenStack VM 如何納管，以及節點擴充、單點故障
   和人工依賴。
   要能從自己的設定與輸出回答，並用英文簡述架構與一個故障。

過關須有新環境重建與可控變更的真實輸出、可核對工作、
故障復原、操作手冊、架構決策及技術追問結果。
這些證據支持申請與面試，不能保證錄取或補出學歷、年資、
多人協作及大型生產叢集經驗。Zabbix 與 OpenStack
依實際部署、監控及工作結果描述。

有新 VM 命令或檔案變更時，先在本文件記下用途與影響；
完成後只保留能支持最後成果的命令、輸出和限制。
