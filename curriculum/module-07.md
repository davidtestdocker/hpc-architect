# 模組 07：效能證據、GKE 維運與架構取捨

[能力路線](ROADMAP.md)｜職缺核心：HPC 架構規劃；支撐能力：系統架構。

## 要解決的問題與交付物

模組 06 將在現有 Slurm 叢集建立故障偵測、隔離、修復與工作驗收流程。
本模組要回答兩個架構問題：相近工作換到 GKE，資源、資料與失敗
處理有什麼差異；增加資源後，結果與耗時是否支持擴充決策。

交付可重跑的量測、GKE 正常工作與故障恢復證據，以及一份對照
Slurm 和 GKE 的架構決策。兩個平台各自排程工作；**整合的是監控
告警入口、事件處理順序和驗收證據**，不把 GKE 當作 Slurm 節點。

## 先看懂量測數字

| 概念 | 白話意思 | 常見誤判 |
|---|---|---|
| 延遲 | 一次工作花多少時間 | 只看平均值，漏掉波動 |
| 吞吐量 | 單位時間完成多少工作 | 單次工作較快，不一定讓整體吞吐變高 |
| 加速比 | 基準耗時 ÷ 新配置耗時 | 用兩個 rank 不代表必然快兩倍 |
| 效率 | 加速相對於增加資源的比例 | 只報加速比，忽略用了多少 CPU／GPU |

例：序列版 10 秒、兩 rank 版 6 秒，加速比是 `10/6 ≈ 1.67`。
還要對照輸入大小、重複量測的波動，以及啟動與通訊成本。
GPU 工作也可能因 CPU→GPU 資料傳輸比計算更耗時而變慢。

## 要比較的資源與工具

下表是量測時要考慮的資源與工具，並非已執行紀錄。

| 資源或工具 | 要確認什麼 |
|---|---|
| CPU、記憶體與 NUMA | 工作是否受核心數、容量或記憶體位置限制 |
| GPU 記憶體與 PCIe | 資料是否放得下、主機和 GPU 間傳輸是否成為瓶頸 |
| NIC 與共享儲存 | 跨節點通訊及讀寫是否限制吞吐 |
| `time`、Slurm 工作紀錄 | 工作耗時與執行位置 |
| `lscpu`、`/proc`、檔案系統統計 | 量測時的資源背景 |

必要時才選 `perf` 或網路、I/O 工具，並先確認權限與採樣開銷。
每次量測都要記輸入、版本、rank 數、節點位置及重複次數；
不從一次結果推論可擴充性。實際命令留待環境與工作確定後記錄。

## GKE 接進哪一段維運流程

Kubernetes 的 **Pod** 是容器工作的執行單位，**Job** 負責讓有限次
工作達到指定完成數。GKE 管理 Kubernetes 叢集與節點；工作重試、
節點修復、監控告警各有自己的條件。Pod 或節點重新建立，不代表
程式從中斷點繼續，也不代表輸出一定正確。

| 模組 06 的事件階段 | GKE 要留下的對應證據 |
|---|---|
| 健康訊號與告警 | Node、Pod 或 Job 狀態、監控指標、告警條件與時間 |
| 隔離與定位 | 哪個節點或工作無法運作、控制器及日誌指出的原因 |
| 修復與重試 | GKE、Kubernetes 或管理者各做了什麼；重試次數與停止條件 |
| 恢復與驗收 | 告警恢復、最終工作狀態、輸入與可核對輸出 |

先核對 GKE 原生監控、日誌與告警通路，再決定如何與模組 06 的
Zabbix 告警匯入**同一個可實際接收的事件入口**。入口可以是同一
告警平台或共同的事件接收通路，但須有兩邊的真實事件與時間可對照；
只在文件中並列兩張截圖不算整合。選型要說明資料來源、權限、
成本、延遲與失聯時能看見什麼；實際方式待環境確認後記錄。

## 實作與過關證據

1. 用已有的可核對答案工作，至少比較兩種 CPU 配置，各重複量測三次。
2. 比較 CPU 與單 GPU 工作的答案、資料量、耗時與卡的使用情況；演算法或精度不同時不直接宣稱加速。
3. 保留原始 CSV、程式版本與環境；分析變快或變慢的原因，提出下一個可驗證改進。
4. 為教學叢集擴展成企業叢集做設計：按工作型態估 CPU／GPU／記憶體、網路、儲存和電力，說明單點故障、高可用、成本與維運取捨。
5. 先估 GKE 叢集、節點與儲存成本並取得同意，再部署最小可行環境；
   選一份適合容器化、答案可核對的代表性工作，保存工作定義、輸入、
   資料路徑、資源請求、Pod／Job 狀態、日誌與正確結果。
   若與 Slurm 使用不同實作或硬體，明確標示可比較與不可比較的部分。
6. 在沒有重要工作且已準備復原方式時，演練一個可復原的 GKE 工作
   或節點故障。保留故障前後狀態、監控告警、失敗原因、控制器或
   管理者的處理、重試條件及最後結果。核對重跑有無重複寫入或
   覆寫；若只演練 Job 故障，就不宣稱驗證了節點自動修復。
7. 把模組 06 的 Slurm 事件與本模組的 GKE 事件接進共同告警入口。
   用相同欄位記錄平台、時間、受影響資源、工作、處理者、恢復
   條件與驗收結果，核對兩邊事件都可被接收與追查。
8. 對照相近工作在 Slurm 與 GKE 的資源請求、排程、資料路徑、
   失敗處理、監控責任與操作成本；只比較條件一致的耗時，
   並標明實際驗證規模與未驗證假設。

設計要標明哪些是實測、哪些只是規格推估。
L4 可用來驗證單卡排程與某些工作；FP64 科學計算或多卡訓練要另選合適機型。
單卡 VM 不能驗證 NVLink、跨 GPU 通訊、RDMA、實體交換器或機櫃供電。
Slurm 是作業排程器，K8s 管容器工作負載；
GKE 是本模組執行 K8s 工作的環境，不把平台操作等同 HPC 排程經驗。

原始量測與可重跑分析放在 `project/benchmarks/`，不含憑證的
Kubernetes 工作與監控設定放在 `project/` 對應目錄；故障證據放在
`project/incidents/`，架構決策放在 `project/docs/`。
過關須有**GKE 正常工作、一次故障與恢復、可核對的最終結果、
兩平台共同告警入口的實際證據、原始量測與架構決策**。
只有 Pod 重新啟動或 Job 顯示完成，沒有輸出正確性與事件鏈，
不足以證明故障恢復。完成後保存 GKE 資源清除證據，並標明
哪些是實測、哪些是規格推估；教學叢集不稱為大型生產經驗。

執行後才記實際數字與判讀。
