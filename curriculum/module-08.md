# 模組 08：面試作品與職缺能力證據

[能力路線](ROADMAP.md)｜目標：把核心工作與程式能力整理成可檢查的作品。

## 這個模組在做什麼

把前面交付的程式、部署、量測與故障紀錄整理成別人能重建和追問的作品，
再把每項職缺要求對到具體證據，準備可誠實說明的展示與履歷內容。

## 目前狀態

**未開始實作。** 本文件記錄作品重建與面試展示的目標。

## 作品要讓別人看見什麼

作品應讓別人依文件重建、測試，並能追問每個設計決定。
檔案、命令結果與原始資料要能支持履歷中的說法：

| 履歷主張 | 需要的證據 |
|---|---|
| 設計叢集 | 需求、拓撲、資源與成本取捨 |
| 部署叢集 | 可重建步驟、實際節點與工作結果 |
| 自動化 | 部署程式、重跑結果與非預期變更判讀 |
| 維運與復原 | 真實事件的症狀、定位、修復及工作復測 |
| 效能改善 | 可比的原始量測、分析方法與改善前後結果 |

例：若只完成跨節點工作，就寫「建置並驗證跨節點工作」；
沒有改善前後量測，就不能寫「優化叢集效能」。
教學規模 GCP 叢集可證明方法與操作，不能代表企業硬體規模、
實體高速網路或多年工作經驗，也不能虛構合作經歷。

## 檢查方式

下表是未來交付作品時的檢查方式，並非已完成的驗證。

| 材料 | 讀者要能做什麼 |
|---|---|
| Git 提交或版本標籤 | 找到與展示對應的交付版本 |
| README／操作手冊 | 找到安裝、執行、測試與復原步驟 |
| 工作輸出與原始資料 | 核對節點、結果、退出碼與量測數字 |
| 能力對照表 | 看清每項職缺要求有哪些證據、哪些尚未驗證 |

檢查命令應對應實際程式和部署文件；
不以一條「總測試成功」取代排程、網路、GPU、重建與故障驗證。

## 實作與過關證據

1. 在新環境依文件重建，核對 CPU／GPU 節點、共享資料、程式答案、GPU 分配、部署重跑與故障復原。
2. 準備約十分鐘展示：需求與架構、部署、跨節點 CPU 工作、單 GPU 工作、故障、量測和限制。
3. 對照職缺原文逐項寫「要求 → 實際證據 → 尚未驗證範圍」。
4. 練習現場修改 Python 或 C/C++、查 Slurm 工作與 GPU GRES、診斷網路或權限；用中文完整說明，再用英文簡述架構與一個故障。

過關須有可重建專案、測試與原始證據、操作與復原手冊、架構取捨，
以及能誠實寫入履歷的成果。學歷與年資不能靠課程補出；
OpenStack、K8s 或 Zabbix 若未實作，只能描述概念，不能寫成經驗。

有新 VM 命令或檔案變更時，先在本文件記下用途與影響；
完成後只保留能支持最後成果的命令、輸出和限制。
