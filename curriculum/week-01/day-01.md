## 今日目標與課前筆記

HPC 將計算工作分配到多個運算資源；登入、排程、運算與儲存有不同責任。

一般線上服務多半持續運行，關注可用性、延遲與吞吐量。HPC 常見工作則有明確的開始和結束，例如「使用 8 個 CPU 核心處理一批資料，最多執行 30 分鐘」。兩者都涉及資源、權限、網路、儲存及故障處理，但工作生命週期不同。

```text
使用者準備程式、資料與資源需求
  ↓
登入／提交節點將工作交給排程器
  ↓
控制器等待並分配合適資源
  ↓
運算節點執行程式並讀寫資料
  ↓
結果存入共享或本機儲存
  ↓
使用者檢查結果與退出狀態
```

四個基本角色：

- 登入／提交節點：準備、編譯及提交工作。
- 控制器／排程器：追蹤節點和工作狀態，決定資源配置。
- 運算節點：實際執行程式。
- 儲存系統：保存程式、輸入資料與結果。

排程器只負責配置資源，不會自動把普通程式變成平行程式。程式還需要 MPI、多程序、工作切分或其他平行方法；實際速度也受序列工作、通訊、儲存和資源競爭影響。

教學環境可以讓登入入口、控制器和 NFS 共用 head 節點，以降低成本；這是實驗取捨，不代表生產架構一定如此。

## 我的實作紀錄（不可用預期結果冒充）

### 1. 確認目前使用者：`whoami`

**目的**

確認目前 shell 中指令是以哪個有效使用者身分執行。Linux 會依使用者與群組身分判斷檔案存取和系統操作權限。

**實際操作與輸出**

```console
[root@instance-20260923-104239 hpc-arch]# whoami
root
```

**結果解釋**

`whoami` 輸出 `root`，表示這個 shell 的有效使用者是 `root`。`root` 的 UID 固定為 0，通常能讀寫系統檔案、管理使用者、安裝套件及啟停服務。提示字元中的 `root@instance-20260923-104239` 也顯示「使用者@主機名」，結尾的 `#` 是 root shell 常見提示符，但真正判定依據仍是指令輸出與後續身分查詢，不能只看提示符外觀。

日常操作使用一般帳號能降低誤改系統的風險；root 留給確實需要系統權限的工作。

### 2. 確認目前主機名稱：`hostname`

**目的**

確認 Linux 核心目前使用的主機名稱。管理多台機器時，主機名稱讓人員、服務及日誌可以辨識事件發生在哪個節點。

**實際操作與輸出**

```console
[root@instance-20260923-104239 hpc-arch]# hostname
instance-20260923-104239
```

**結果解釋**

目前主機名稱是 `instance-20260923-104239`，與 shell 提示符中的主機部分相同。名稱看起來是建立 GCP VM 時產生，但僅憑名稱格式不能確定其建立方式。`hostname` 顯示本機核心目前保存的名稱；它不會證明 DNS 或 `/etc/hosts` 可以解析此名稱，也不能證明重新啟動後一定保持相同設定。

### 3. 確認 Linux 發行版：`cat /etc/os-release`

**目的**

確認作業系統發行版與版本，避免將其他 Linux 發行版的套件名稱、服務設定或安裝步驟直接套用到目前環境。

**實際操作與重點輸出**

```console
NAME="AlmaLinux"
VERSION="10.2 (Lavender Lion)"
ID_LIKE="rhel centos fedora"
```

**結果解釋**

目前 VM 使用 AlmaLinux 10.2，版本標示為 stable。`ID_LIKE` 表示它與 RHEL、CentOS、Fedora 生態系有相容關係；本機套件管理預期會使用 `dnf`。之後查安裝文件時，優先選 AlmaLinux 10 或 RHEL 10 相容版本，不能直接照搬 Ubuntu 的 `apt` 指令。

### 4. 確認 Linux 核心版本：`uname -r`

**目的**

確認目前正在執行的 Linux kernel 版本與硬體架構。核心版本會影響核心模組、驅動程式與部分系統工具的相容性。

**實際操作與重點輸出**

```console
6.12.0-211.43.1.el10_2.x86_64
```

**結果解釋**

`6.12.0` 是 kernel 版本；`211.43.1.el10_2` 是 AlmaLinux／Enterprise Linux 10.2 對應的套件建置版本；`x86_64` 表示 64 位元 x86 架構。發行版版本（AlmaLinux 10.2）和 kernel 版本（6.12.0）是不同概念：前者決定作業系統生態與套件管理，後者決定目前運行的核心。

### 5. 觀察 CPU 拓撲：`lscpu`

**目的**

確認作業系統可使用的 CPU 數量、客體看到的拓撲與虛擬化資訊。程式的平行數量和日後排程器的資源設定都以這些可見資源為起點。

**實際操作與重點輸出**

```console
Architecture:                x86_64
CPU(s):                      2
Vendor ID:                   GenuineIntel
Model name:                  Intel(R) Xeon(R) CPU @ 2.20GHz
Thread(s) per core:          2
Core(s) per socket:          1
Socket(s):                   1
Hypervisor vendor:           KVM
Virtualization type:         full
NUMA node(s):                1
```

**結果解釋**

這台 VM 可排程 2 個邏輯 CPU，符合原先的 2 vCPU 估計。客體拓撲顯示 1 socket、每個 socket 1 core、每個 core 2 threads；兩條 thread 是同一核心的硬體執行緒，不等於兩個獨立實體核心。`KVM` 與 `full` 表示這是完整虛擬化環境，因此 CPU 型號、快取大小和 NUMA 資訊是客體可見資訊，不能直接當成專屬實體主機規格。

CPU flags 包含 `avx` 與 `avx2`，代表此環境可使用這兩種向量指令集；輸出中沒有 `avx512`。目前只看到一個 NUMA 節點，這個小型 VM 不適合用來練習跨 NUMA 的效能差異。

### 6. 觀察記憶體與 swap：`free -h`

**目的**

確認系統可見記憶體、目前可用量和 swap 狀態。這些資訊可用於判斷工作是否可能因記憶體不足而失敗。

**實際操作與重點輸出**

```console
               total        used        free      shared  buff/cache   available
Mem:           3.8Gi       1.4Gi       1.7Gi        16Mi       1.0Gi       2.5Gi
Swap:             0B          0B          0B
```

**結果解釋**

系統總記憶體為 3.8 GiB，符合 4 GB VM 的預期；Linux 以 GiB 顯示，所以數值不會剛好等於 4。`used` 是目前已使用量，`free` 是完全未使用記憶體，`buff/cache` 主要是可在需要時回收的快取。判斷還能分配多少記憶體時，優先看 `available`，目前是 2.5 GiB，而不是只看 `free` 的 1.7 GiB。

Swap 為 0，表示沒有交換空間。記憶體耗盡時，系統沒有 swap 可緩衝，可能直接觸發 OOM killer 終止某個程序；因此這台 VM 的測試工作需要保持小型。

### 7. 觀察磁碟、分割區與掛載點：`lsblk`

**目的**

列出區塊裝置、分割區、檔案系統與掛載點，確認磁碟實際如何提供給作業系統使用。

**實際操作與重點輸出**

```console
NAME    SIZE TYPE FSTYPE MOUNTPOINTS
sda      10G disk
├─sda1  200M part vfat   /boot/efi
└─sda2  9.8G part xfs    /
sdb     100G disk
```

**結果解釋**

`sda` 是 10 GB 系統磁碟。它的 `sda1` 為 200 MB 的 EFI 開機分割區，`sda2` 為約 9.8 GB 的 XFS 檔案系統，掛載在根目錄 `/`。因此目前作業系統、套件和預設使用者目錄都使用這個約 10 GB 的根檔案系統。

`sdb` 是另一顆 100 GB 磁碟，但沒有顯示 `FSTYPE` 或 `MOUNTPOINTS`，表示它尚未建立檔案系統，也沒有掛載。它目前不能當成可直接使用的資料目錄。格式化與掛載會改變系統狀態，這一天只做觀察；後續確認用途與資料安全後才處理。

### 8. 確認根檔案系統可用空間：`df -hT /`

**目的**

確認根目錄 `/` 使用的檔案系統類型、容量、使用量和可用空間。

**實際操作與重點輸出**

```console
Filesystem     Type  Size  Used Avail Use% Mounted on
/dev/sda2      xfs   9.8G  4.3G  5.6G  44% /
```

**結果解釋**

根目錄 `/` 使用 `/dev/sda2` 上的 XFS，總容量 9.8 GB，已使用 4.3 GB，可用 5.6 GB，使用率 44%。這與前一步 `lsblk` 看到的 `sda2` 一致。`df` 顯示的是已掛載檔案系統的實際空間，因此看不到尚未掛載的 100 GB `sdb`。日後安裝套件、編譯程式或保存資料前，應先檢查根目錄是否有足夠空間。

### 9. 查看介面與 IP 位址：`ip -brief addr`

**目的**

快速列出網路介面、狀態與已配置的 IP 位址。

**實際操作與重點輸出**

```console
lo               UNKNOWN        127.0.0.1/8 ::1/128
eth0             UP             10.140.0.2/32 fe80::2725:28ff:b62c:9e10/64
```

**結果解釋**

`lo` 是 loopback 介面，`127.0.0.1` 與 `::1` 都指向本機；loopback 顯示 `UNKNOWN` 是常見狀態。`eth0` 是目前主要網路介面，狀態為 `UP`，IPv4 位址是 `10.140.0.2/32`。`10.0.0.0/8` 是私有位址範圍，表示這是 GCP VPC 的內部位址，不是公開網際網路位址。

`/32` 表示此介面設定的是單一 IPv4 主機位址。雲端 VM 可透過路由表與閘道到達其他網段，所以 `/32` 不代表只能與自身通訊；下一步需要查看路由表。`fe80::.../64` 是 IPv6 link-local 位址，只能在同一條網路鏈路使用。`UP` 只代表介面已啟用，尚不能證明可到達其他主機。

### 10. 查看路由表：`ip route`

**目的**

查看封包離開本機時，系統依目的位址選擇的下一跳與網路介面。

**實際操作與重點輸出**

```console
default via 10.140.0.1 dev eth0 proto dhcp src 10.140.0.2 metric 100
10.140.0.1 dev eth0 proto dhcp scope link src 10.140.0.2 metric 100
```

**結果解釋**

第一條是預設路由：沒有更具體路由可用時，封包從 `eth0` 以來源位址 `10.140.0.2` 送到閘道 `10.140.0.1`。第二條表示此閘道可直接透過 `eth0` 到達。兩條規則的 `proto dhcp` 表示由 DHCP 設定；`metric 100` 是路由成本，若有多條符合路由，通常選 metric 較低者。這證實 `10.140.0.2/32` 雖是單一主機位址，仍能經由閘道前往其他目的地。

### 概念題標準答案

1. 增加兩台 VM 不會讓原本的單一 Python 程式自動變快。程式需要改成多程序、MPI、Dask、Ray 或其他平行架構，並切分工作與資料，才可能使用多台機器。
2. 不同。工作等待時，先查排程狀態與原因，例如資源、分區或節點問題；工作已啟動但找不到檔案時，先查執行節點的路徑、掛載和權限。
3. 不夠。控制器正常以外，還要驗證運算節點、身分驗證、名稱解析、網路、資料路徑、工作實際輸出與退出狀態。
4. 目前 VM 適合驗證 Linux 管理、Shell、Python、單機 C／MPI、單節點排程器概念、基本監控與小型自動化。多節點工作分配、跨主機 SSH／共享儲存、跨節點 MPI、節點故障處理及網路測試需要多台獨立 VM。真實 CPU 拓撲、NUMA、GPU、RDMA／InfiniBand 和可代表生產效能的量測需要相應實體硬體。
5. `The controller manages jobs and allocates resources.` `A compute node runs the assigned program.` `A job is a request to run a program with specific resources.`
