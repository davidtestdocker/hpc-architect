## 今日目標與課前筆記

HPC 將計算工作分配到多個運算資源；登入、排程、運算與儲存有不同責任。

一般線上服務多半持續運行，關注可用性、延遲與吞吐量。HPC 常見工作則有明確的開始和結束，例如「使用 8 個 CPU 核心處理一批資料，最多執行 30 分鐘」。兩者都涉及資源、權限、網路、儲存及故障處理，但工作生命週期不同。

```text
使用者準備程式、資料與資源需求
  ↓
登入／提交節點將工作交給排程器
  ↓
控制器等待並分配合適資源
  ↓
運算節點執行程式並讀寫資料
  ↓
結果存入共享或本機儲存
  ↓
使用者檢查結果與退出狀態
```

四個基本角色：

- 登入／提交節點：準備、編譯及提交工作。
- 控制器／排程器：追蹤節點和工作狀態，決定資源配置。
- 運算節點：實際執行程式。
- 儲存系統：保存程式、輸入資料與結果。

排程器只負責配置資源，不會自動把普通程式變成平行程式。程式還需要 MPI、多程序、工作切分或其他平行方法；實際速度也受序列工作、通訊、儲存和資源競爭影響。

教學環境可以讓登入入口、控制器和 NFS 共用 head 節點，以降低成本；這是實驗取捨，不代表生產架構一定如此。

## 我的實作紀錄（不可用預期結果冒充）

### 1. 確認目前使用者：`whoami`

**目的**

確認目前 shell 中指令是以哪個有效使用者身分執行。Linux 會依使用者與群組身分判斷檔案存取和系統操作權限。

**實際操作與輸出**

```console
[root@instance-20260923-104239 hpc-arch]# whoami
root
```

**結果解釋**

`whoami` 輸出 `root`，表示這個 shell 的有效使用者是 `root`。`root` 的 UID 固定為 0，通常能讀寫系統檔案、管理使用者、安裝套件及啟停服務。提示字元中的 `root@instance-20260923-104239` 也顯示「使用者@主機名」，結尾的 `#` 是 root shell 常見提示符，但真正判定依據仍是指令輸出與後續身分查詢，不能只看提示符外觀。

**目前限制／待確認**

目前只知道有效使用者名稱，尚未確認 UID、群組、登入帳號來源與是否可使用 `sudo`；這些不是 `whoami` 能回答的問題。日常操作使用一般帳號能降低誤改系統的風險；root 留給確實需要系統權限的工作。

- 環境：GCP Linux VM；詳細 OS 與硬體資訊待後續指令確認。
- 問題 → 假設 → 檢查 → 修正 → 再驗證：目前沒有故障；已辨識日常操作不宜長期使用 root，後續身分與帳號課程再驗證。

### 2. 確認目前主機名稱：`hostname`

**目的**

確認 Linux 核心目前使用的主機名稱。管理多台機器時，主機名稱讓人員、服務及日誌可以辨識事件發生在哪個節點。

**實際操作與輸出**

```console
[root@instance-20260923-104239 hpc-arch]# hostname
instance-20260923-104239
```

**結果解釋**

目前主機名稱是 `instance-20260923-104239`，與 shell 提示符中的主機部分相同。名稱看起來是建立 GCP VM 時產生，但僅憑名稱格式不能確定其建立方式。`hostname` 顯示本機核心目前保存的名稱；它不會證明 DNS 或 `/etc/hosts` 可以解析此名稱，也不能證明重新啟動後一定保持相同設定。

**目前限制／待確認**

目前只確認本機主機名稱，尚未驗證完整網域名稱、名稱解析來源、其他節點能否解析，以及 GCP 中停止或重建 VM 後的名稱行為。多台機器互動時，名稱必須唯一且一致，否則容易出現設定、連線和日誌對不上的問題。
